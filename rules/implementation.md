# 実装方針規程

実装に用いる道具立ての選定と扱いを定める。記述方法はコーディング規程による。

## 参照仕様の確認

確認義務は本項に一元化し、各規程に重複して置かない。

- ライブラリ・ツールの利用前に、公式リファレンスで現行の API と推奨パターンを確認する。既知でも省略せず、記憶のみで判断しない。
- メジャーバージョン更新時は公式の移行ガイドを確認する。
- 公式リファレンスに実装例がある場合は、その形に忠実に実装し、説明に出典を添える。
- 非推奨の API を使用しない。
- 規程の適用前も同様に確認し、現行仕様と異なる・非推奨を含む・実態と乖離する記述は適用しない。該当を認めた場合は、依頼範囲外でも対象ファイル・該当箇所・相違・修正案を自発的に提示する。
- 規程と公式の推奨が衝突する場合は、いずれにも倒さず利用者に確認する。

## 雛形の生成

- プロジェクト・構成ファイルの雛形は、可能な限り公式のコマンドラインツールで生成する。
- 生成されたファイルは原則無改変で維持し、改変する場合は理由を提示する。

## 依存関係とパッケージ管理

- Node.js プロジェクトのパッケージマネージャは pnpm とする。
- 依存関係の追加時は必要性を提示する。
- 依存関係の導入時は、その時点の最新の安定版を用いる。プレリリース版は用いない。
- 出所不明・保守停止のパッケージを採用しない。
- ロックファイルはバージョン管理に含める。
- 依存関係は自動更新の対象に含める。
- 依存関係の更新は、マイナー・パッチのみを対象とする。メジャーは自動更新の対象とせず、更新の要否は設計の見直しとして判断する。

## バージョン

- バージョンはセマンティックバージョニングによる。破壊的変更はメジャー、後方互換の機能追加はマイナー、不具合修正はパッチとする。
- バージョンは一箇所で管理し、複数箇所に記載しない。
