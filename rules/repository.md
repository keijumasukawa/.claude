# リポジトリ運用規程

変更の記録から統合・公開までの運用と、その自動実行の原則を定める。

## ブランチ戦略

GitHub Flow とする。

- `main` は常にデプロイ可能に保つ。
- 変更は `main` から作業ブランチを分岐し、プルリクエストで統合する。
- ブランチ名は `<接頭辞>/<説明>` とし、接頭辞はプルリクエストのタイトルの接頭辞と一致させる。説明は変更内容が一目で分かる短い名称とし、固定名を使い回さない。
- 不要になったローカルの作業ブランチは、次の作業開始時に削除する。リモートの削除は「リポジトリの設定」による。

## リポジトリの初期化

- 初期化は Issue に紐づけない。手順は `init-repo` スキルによる。
- 初期化後のファイルの追加・変更は、すべてプルリクエストを経由する。
- プルリクエスト・Issue のテンプレートは `.github` リポジトリの既定を用い、各リポジトリには置かない。

## コミット

- コミット前に、リポジトリが定める検証コマンド(lint、型検査、テスト等)の通過を確認する。対象はリポジトリの構成から判断する。
- メッセージは Conventional Commits 形式とし、接頭辞に続く説明は日本語。件名は1行、本文は原則付さない。
- 自動生成されるコミットは、説明の日本語化を要しない。

接頭辞は次の9種とし、複数にまたがる変更は支配的な意図の型を用いる。

| 接頭辞 | 用途 |
| --- | --- |
| `feat:` | 新機能の追加 |
| `fix:` | バグの修正 |
| `docs:` | 文書のみの変更 |
| `refactor:` | 動作を変えない内部構造の変更 |
| `perf:` | パフォーマンスの改善 |
| `test:` | テストコードの追加・修正 |
| `ci:` | 継続的インテグレーションの設定変更 |
| `chore:` | 依存関係、設定ファイル、その他の雑務 |
| `revert:` | 以前のコミットの取り消し |

接頭辞はコミットメッセージとプルリクエストのタイトルに用いる。Issue は対応すべき事象を表すため、Issue タイトルには用いない。

## プルリクエスト

- タイトルは Conventional Commits 形式。
- 本文はテンプレートの全項目を記入し、具体的な数値や、識別子・コマンド等の実装の詳細を書かない。
- プルリクエスト・Issue・リリースノートの本文は体言止めで簡潔に記載し、各項目の内容は件数によらず箇条書きとする。
- Issue に対応する場合は `Closes #<Issue番号>` を記載する。
- 単独でマージできる変更はプルリクエストを分け、不可分な変更は分けない。規模は300〜400行以下を目安とし、超える場合は分割を検討する。
- 作成後はレビュー待ちと報告して作業を終え、マージを前提とした後続作業をしない。

## ワークフロー

- ワークフローの表示名(`name`)は、処理内容を表す英語句の Title Case とする。
- ワークフローのファイル名は、表示名を小文字の kebab-case にしたものとする。
- ジョブ名(`<job_id>`)は、処理内容を表す英語の動詞または動詞句の kebab-case とする。必須ステータスチェックが参照する識別子であるため、ジョブの表示名(`name`)を別途指定しない。
- ステップの表示名(`name`)は任意とする。処理の意図が記述から読み取れない場合に付し、日本語で記述してよい。
- 共有データベースへの書き込みを伴う操作(マイグレーション、シード、バッチ)は、すべてワークフローとして定義する。手動実行は `workflow_dispatch` に限定し、ローカルからの直接実行を行わない。ダッシュボード等での読み取りは対象としない。
- 同一の資源へ書き込む複数のワークフローは、共通の `concurrency` グループで排他する。実行中のジョブを取り消さず、待機した実行も取りこぼさずに順次実行する。書き込みの中断と欠落を避けるためである。

## リポジトリの設定

GitHub 上で行い、利用者が管理する。本規程は意図のみを定め、機能名・手順は GitHub の現行仕様による。

- `main` への直接 push を禁止する。統合はプルリクエストのマージのみとする。
- マージ方式は Squash and merge のみを許可する。1つのプルリクエストが `main` 上の1コミットとなり、履歴が変更の単位と一致するためである。
- squash コミットの既定メッセージはプルリクエストのタイトルとする。
- マージの条件は、継続的インテグレーションの全通過とする。
- マージ後のリモートブランチの削除を有効にする。

## リリース

- リリースは `main` へのマージ済みを前提とする。
- タグは `v<バージョン>` とする。
- 手順は `release` スキルによる。

## README の例外

- README の変更は Issue を伴わない単独のプルリクエストとし、他のファイルを含めない。
- 手順は `update-readme` スキルによる。
